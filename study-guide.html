Part 1: Foundations

Data engineering builds the reliable systems that move raw data from where it is created to where people and models can trust and use it. The job is less about any one tool than about correctness, recoverability, and cost at scale.

Ten principles to carry through every part

  1. Keep raw data immutable, so any downstream result can be rebuilt.

  2. Make every job idempotent. Retries and backfills then become safe and routine.

  3. Assume duplicates, late data, and out-of-order data will happen.

  4. Separate logical time from wall-clock time. A job for 2026-11-05 must behave the same whenever it runs.

  5. Prefer boring technology until requirements prove otherwise. Batch beats streaming unless latency pays for it.

  6. Treat data as a product, with owners, documentation, and SLOs.

  7. Test data as well as code. Valid code can still produce wrong numbers.

  8. Know the grain of every table before you join it.

  9. Make cost visible. Every design choice has a compute and storage bill.

  10. Design for failure: alert on it, make it easy to diagnose, and make recovery a single command.

You know this part when you can explain the difference between ETL and ELT, and why a non-idempotent pipeline makes backfills dangerous.

Eight patterns to memorize

1. Deduplicate to the latest record. This is the most common pattern in pipelines.

WITH ranked AS (
  SELECT *,
         ROW_NUMBER() OVER (
           PARTITION BY customer_id
           ORDER BY updated_at DESC, ingested_at DESC
         ) AS rn
  FROM raw_customers
)
SELECT * FROM ranked WHERE rn = 1;
-- Snowflake, BigQuery, and Databricks can shorten this with QUALIFY rn = 1

2. Running total and 7-day moving average.

SELECT order_date,
       revenue,
       SUM(revenue) OVER (ORDER BY order_date
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
       AVG(revenue) OVER (ORDER BY order_date
         ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS avg_7d
FROM daily_revenue;

3. Gaps and islands: find consecutive active days.

WITH numbered AS (
  SELECT user_id, activity_date,
         DATEADD(day,
           -ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY activity_date),
           activity_date) AS island
  FROM (SELECT DISTINCT user_id, activity_date FROM events) d
)
SELECT user_id, MIN(activity_date) AS start_date,
       MAX(activity_date) AS end_date, COUNT(*) AS streak_days
FROM numbered
GROUP BY user_id, island;

4. Sessionization: a new session after 30 idle minutes.

WITH flagged AS (
  SELECT user_id, event_ts,
         CASE WHEN LAG(event_ts) OVER (PARTITION BY user_id ORDER BY event_ts)
                   >= event_ts - INTERVAL '30' MINUTE
              THEN 0 ELSE 1 END AS is_new_session
  FROM events
)
SELECT user_id, event_ts,
       SUM(is_new_session) OVER (PARTITION BY user_id ORDER BY event_ts
         ROWS UNBOUNDED PRECEDING) AS session_id
FROM flagged;

5. Anti-join: customers with no orders.

SELECT c.customer_id
FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
);

6. Date spine: show zero for days with no sales.

SELECT d.calendar_date, COALESCE(SUM(s.amount), 0) AS revenue
FROM dim_date d
LEFT JOIN sales s ON s.sale_date = d.calendar_date
WHERE d.calendar_date BETWEEN '2026-01-01' AND '2026-12-31'
GROUP BY d.calendar_date;

7. Grain test: run this before you trust any table or join.

SELECT order_id, COUNT(*)
FROM fct_orders
GROUP BY order_id
HAVING COUNT(*) > 1;   -- any row returned means the grain is not what you assumed

8. Idempotent upsert.

MERGE INTO dim_customer t
USING staged_customer s ON t.customer_id = s.customer_id
WHEN MATCHED AND s.updated_at > t.updated_at THEN
  UPDATE SET email = s.email, updated_at = s.updated_at
WHEN NOT MATCHED THEN
  INSERT (customer_id, email, updated_at)
  VALUES (s.customer_id, s.email, s.updated_at);

Reading query plans

Columnar engines have no B-tree indexes to save you, so performance comes from reading less data.

  • Select only the columns you need. Column stores pay for each column scanned.

  • Filter on the partition or cluster key, and keep it sargable. WHERE order_date >= '2026-01-01' prunes files, while WHERE YEAR(order_date) = 2026 may not.

  • Learn the join types in EXPLAIN: hash, merge, nested loop, and broadcast versus shuffle.

  • Look at bytes scanned, partitions pruned, and any exploding row counts.

  • Filter before you join, and aggregate before you join when the grain allows it.

A production-shaped extractor

This example shows the habits interviewers look for: streaming pagination, bounded retries, a deterministic output path, and an atomic write.

import logging
import os
from collections.abc import Iterator
from datetime import date
from pathlib import Path

import httpx
import polars as pl
from tenacity import retry, retry_if_exception_type, stop_after_attempt, wait_exponential

log = logging.getLogger(__name__)

@retry(
    retry=retry_if_exception_type(httpx.TransportError),
    stop=stop_after_attempt(5),
    wait=wait_exponential(multiplier=1, max=60),
)
def fetch_page(client: httpx.Client, url: str, params: dict) -> dict:
    resp = client.get(url, params=params, timeout=30)
    resp.raise_for_status()
    return resp.json()

def iter_orders(client: httpx.Client, url: str, day: date) -> Iterator[list[dict]]:
    params = {'updated_date': day.isoformat(), 'limit': 1000}
    while True:
        page = fetch_page(client, url, params)
        yield page['results']
        if not page.get('next_cursor'):
            return
        params['cursor'] = page['next_cursor']

def load_day(url: str, day: date, root: Path) -> Path:
    # The path depends only on the logical date, so a rerun replaces the same output.
    target = root / f'orders/dt={day:%Y-%m-%d}/data.parquet'
    target.parent.mkdir(parents=True, exist_ok=True)
    tmp = target.with_suffix('.tmp')
    with httpx.Client() as client:
        pages = [pl.DataFrame(p) for p in iter_orders(client, url, day) if p]
    if not pages:
        log.warning('no rows', extra={'day': str(day)})
    frame = pl.concat(pages, how='diagonal_relaxed') if pages else pl.DataFrame()
    frame.write_parquet(tmp)
    os.replace(tmp, target)   # atomic on a local file system
    log.info('loaded', extra={'day': str(day), 'rows': frame.height})
    return target

This version still holds one day in memory. In an interview, say so, then explain how you would write one file per page instead. On object storage, os.replace does not apply, so use a write-then-commit pattern or a table format.

Part 4: Data modeling

Data modeling is the highest-return skill to learn, because tools change while grain, keys, and history do not. In the 2026 survey, Kimball was the most common named method at 27.8%, and data modeling was the second most requested training topic.

The four-step dimensional design

  1. Choose the business process. Example: answering a phone call.

  2. Declare the grain. One row per what, exactly? Example: one row per completed call.

  3. Choose the dimensions. The context around the event: who, what, where, when.

  4. Identify the facts. The numeric measures at that grain: duration, cost, sentiment score.

Get the grain wrong and everything built on it is wrong. State it in one sentence at the top of every model.

Worked example: a call center star schema

CREATE TABLE dim_customer (
  customer_sk    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- surrogate key
  customer_id    VARCHAR NOT NULL,        -- natural key from the source
  segment        VARCHAR,
  state          VARCHAR,
  valid_from     TIMESTAMP NOT NULL,      -- SCD type 2 columns
  valid_to       TIMESTAMP,
  is_current     BOOLEAN NOT NULL
);

CREATE TABLE dim_date (
  date_sk        INT PRIMARY KEY,         -- 20261105
  calendar_date  DATE NOT NULL,
  fiscal_quarter VARCHAR,
  is_holiday     BOOLEAN
);

-- Grain: one row per completed inbound call.
CREATE TABLE fct_call (
  call_id        VARCHAR NOT NULL,        -- degenerate dimension
  date_sk        INT NOT NULL REFERENCES dim_date,
  customer_sk    BIGINT NOT NULL REFERENCES dim_customer,
  agent_sk       BIGINT NOT NULL,
  queue_sk       BIGINT NOT NULL,
  duration_sec   INT,                     -- additive
  hold_sec       INT,                     -- additive
  was_resolved   SMALLINT                 -- additive 0 or 1 flag
);

Joining fct_call to dim_customer on the surrogate key returns the customer's attributes as they were at the time of the call. That is the point of the surrogate key.

Type 2 is the interview favorite. Here is the merge logic, which closes old rows and inserts new versions:

MERGE INTO dim_customer t
USING (
  -- Rows with a NULL key always insert. Changed customers appear twice:
  -- once to close the old row and once to insert the new one.
  SELECT s.customer_id AS merge_key, s.* FROM staged s
  UNION ALL
  SELECT NULL AS merge_key, s.*
  FROM staged s
  JOIN dim_customer d
    ON d.customer_id = s.customer_id AND d.is_current
  WHERE d.segment IS DISTINCT FROM s.segment
) src
ON t.customer_id = src.merge_key AND t.is_current
WHEN MATCHED AND t.segment IS DISTINCT FROM src.segment THEN
  UPDATE SET valid_to = src.updated_at, is_current = FALSE
WHEN NOT MATCHED THEN
  INSERT (customer_id, segment, valid_from, valid_to, is_current)
  VALUES (src.customer_id, src.segment, src.updated_at, NULL, TRUE);

Common modeling mistakes

  • Mixing grains in one table, such as order lines and order totals

  • Using natural keys that change or get reused

  • Storing only current state when the business will ask about the past

  • Averaging averages, or summing a snapshot across time

  • Building for one dashboard instead of the business process

  • Leaving ownership and metric definitions undocumented

Part 5: Storage engines, file formats, and database internals

Physical layout decides most query speed and cost, because the fastest data to process is the data you never read. Understanding why columnar storage works lets you predict performance without running a benchmark.

Storage engine structures

  • B-tree: updates pages in place and reads fast. It suits OLTP databases.

  • LSM tree: buffers writes in memory, flushes sorted files, and compacts them later. It suits heavy writes (RocksDB, Cassandra, Kafka Streams state).

  • Write-ahead log: records each change before applying it. It enables crash recovery, replication, and log-based CDC.

  • MVCC: keeps multiple row versions so readers do not block writers. Table formats apply a similar idea at the file level through snapshots.

Learn the isolation levels: read committed, repeatable read, snapshot, and serializable. Be ready to explain write skew and lost updates.

Inside a Parquet file

Parquet's structure explains why it is fast. A file holds row groups, each row group holds one column chunk per column, and each chunk holds pages. The footer stores the schema and per-column minimum and maximum statistics.

  1. The reader opens the footer first.

  2. Column pruning reads only the requested columns.

  3. Predicate pushdown skips row groups whose statistics rule out the filter.

  4. Dictionary and run-length encoding shrink repeated values, then a codec compresses the result.

Sorting data before writing makes the statistics tight, so more data is skipped. Try it yourself:

-- DuckDB
COPY (SELECT * FROM read_csv('trips.csv') ORDER BY pickup_date)
  TO 'trips.parquet' (FORMAT parquet, COMPRESSION zstd, ROW_GROUP_SIZE 1000000);

SELECT row_group_id, path_in_schema, stats_min, stats_max,
       total_compressed_size, encodings
FROM parquet_metadata('trips.parquet');

The small-file problem

Thousands of tiny files slow every query, because the engine pays to list and open each one. Streaming and frequent micro-batches are the usual cause. Compact regularly, aiming for roughly 128 MB to 1 GB per file depending on the engine.

Object storage behavior

  • It is cheap and very durable, and it scales almost without limit.

  • It is a key-value store and not a file system. Directory renames are not atomic, which is one reason table formats exist.

  • S3, ADLS, and GCS all charge for requests, and many small reads add up.

  • ADLS Gen2 with a hierarchical namespace does offer atomic directory renames. Check this for your platform rather than assuming.

  • Egress between regions or clouds can cost more than the compute.

Delivery guarantees

This is a favorite interview topic and one where you have real stories.

True exactly-once delivery across arbitrary systems is not achievable. What people call exactly once is effectively-once processing. Say this in interviews and then explain the mechanism.

Your Solace incident is a direct illustration: at-least-once delivery does not mean the consumer was ready to receive it, and recovery required replay. Practice telling that story using these terms.

A plain INSERT into a table is the non-idempotent trap: every retry adds duplicates. Compare the two:

-- Wrong: a rerun doubles the day's rows
INSERT INTO fct_sales
SELECT * FROM stg_sales WHERE sale_date = '2026-11-05';

-- Right: a rerun replaces the day atomically (Spark SQL)
INSERT OVERWRITE fct_sales PARTITION (sale_date = '2026-11-05')
SELECT order_id, amount FROM stg_sales WHERE sale_date = '2026-11-05';

In Spark, set spark.sql.sources.partitionOverwriteMode=dynamic when you overwrite without naming a partition. Otherwise, a path-based overwrite can wipe the whole table.

Failure modes to design for

  • A worker dies mid-job and its task reruns, so outputs must tolerate retries.

  • A job partly commits, leaving half-written files. Use atomic commits or table formats.

  • A zombie task finishes after being replaced. Use fencing tokens or epochs.

  • A rebalance reassigns a partition while a consumer is still processing it.

  • A slow node drags the whole stage. Speculative execution may help.

  • An upstream API silently returns partial data with a 200 status. Validate row counts.

  • The orchestrator retries a job whose first attempt actually succeeded.

  • A clock skew misorders events if you trust wall-clock timestamps.

Part 7: Batch processing and Spark

Spark remains the standard engine for large-scale batch work, and senior interviews test how it behaves under the hood, not just its API. Most Spark problems are shuffle, skew, or memory problems, so learn to diagnose those three.

Where Spark stands now

Apache Spark 4.2.0 is the third release of the 4.x line and adds change data capture queries, Auto CDC in Declarative Pipelines, and Arrow-optimized Python UDFs by default. The versioning policy moves feature releases to a quarterly cadence from 4.3.0, with 4.5.0 planned as the 4.x long-term support release.

Managed platforms often lag the newest release, so check your runtime's Spark version. Concepts in this part apply across versions.

Architecture

  • Driver: builds the plan, schedules tasks, and holds results you collect.

  • Executors: run tasks and hold cached data. Each has a set number of cores and amount of memory.

  • Cluster manager: provides resources through Kubernetes, YARN, or a managed platform.

  • Hierarchy: an action triggers a job, a job splits into stages at shuffle boundaries, and a stage runs many tasks, one per partition.

  • Spark Connect: a client-server protocol that separates your application from the cluster.

Lazy evaluation and the optimizer

Transformations only build a plan. An action, such as count or write, runs it. This lets the Catalyst optimizer push filters down, prune columns, and reorder joins. Tungsten then generates efficient code and manages memory compactly. Adaptive Query Execution (AQE) adjusts the plan at runtime using real statistics.

    spark.read.parquet('abfss://bronze@lake.dfs.core.windows.net/orders/')
    .filter(F.col('dt') == run_date)           # partition pruning

)

    orders.withColumn('rn', F.row_number().over(latest))
    .filter('rn = 1').drop('rn')
    .join(F.broadcast(customers.select('customer_id', 'segment')),

A safe consumer

Commit offsets only after a durable write. If the process crashes between the two, you reprocess, so the sink must tolerate duplicates.

from confluent_kafka import Consumer, KafkaError

consumer = Consumer({
    'bootstrap.servers': 'localhost:9092',
    'group.id': 'orders-sink',
    'enable.auto.commit': False,
    'auto.offset.reset': 'earliest',
    'isolation.level': 'read_committed',
})
consumer.subscribe(['orders'])

try:
    while True:
        batch = consumer.consume(num_messages=500, timeout=1.0)
        rows = []
        for msg in batch:
            if msg.error():
                if msg.error().code() != KafkaError._PARTITION_EOF:
                    raise RuntimeError(msg.error())
                continue
            rows.append(parse(msg.value()))
        if rows:
            upsert_on_event_id(rows)              # idempotent sink
            consumer.commit(asynchronous=False)   # commit after the write
finally:
    consumer.close()

Why table formats exist

A folder of Parquet files has no transactions, no safe concurrent writes, and slow file listing. A table format adds a metadata layer that tracks exactly which files form each version of a table. That single idea enables:

  • ACID commits on object storage

  • Time travel and rollback

  • Schema and partition evolution without rewriting data

  • Row-level updates and deletes

  • File-level statistics, so planning skips files without listing folders

Planning reads this tree rather than listing folders. The statistics in each manifest let the engine skip files before opening them.

Airflow 3

Airflow 3.0 arrived in April 2025, and 3.3.2 was the current patch as of September 2026. Tutorials written for Airflow 2 can mislead you on these points:

  • Task SDK: DAG code now imports from airflow.sdk.

  • No direct metadata database access from tasks: use the API. Older calls such as DagRun.find break.

  • Assets: Airflow 2's datasets were renamed and expanded for data-aware scheduling.

  • DAG versioning: run history stays tied to the DAG code that ran it.

  • Backfills: these are now managed by the scheduler and can be started from the UI.

  • Remote execution: tasks can run away from the core deployment, which helps in regulated environments.

Two more Airflow 3 changes surfaced while building Project 1. A plain cron string gives a run whose logical date is its trigger time, so use CronDataIntervalTimetable when a run should process the period that just ended. A DAG with depends_on_past=True must also set a reprocess behavior when you create a backfill.

        'retry_exponential_backoff': True,

        day = data_interval_start.strftime('%Y-%m-%d')

Rules for reliable DAGs

  1. Keep tasks idempotent and atomic.

  2. Do no heavy work or network calls at the top level of a DAG file, because the parser runs it constantly.

  3. Pass file paths or IDs in XCom, never the data itself.

  4. Run heavy compute elsewhere: Spark, the warehouse, or a Kubernetes pod.

  5. Use deferrable sensors so waiting does not consume worker slots.

  6. Keep secrets in a backend such as Azure Key Vault.

  7. Parametrize by data interval, and never call now() in business logic.

  8. Test DAG import in CI, and alert on failures and missed SLAs.

Statistical checks you can build

Static thresholds create noise. Use a rolling baseline that respects day-of-week patterns:

WITH daily AS (
  SELECT load_date, COUNT(*) AS row_count
  FROM fct_orders
  GROUP BY load_date
),
scored AS (
  SELECT load_date, row_count,
         AVG(row_count) OVER w AS baseline,
         STDDEV(row_count) OVER w AS sd
  FROM daily
  WINDOW w AS (
    PARTITION BY DAYOFWEEK(load_date)
    ORDER BY load_date
    ROWS BETWEEN 8 PRECEDING AND 1 PRECEDING
  )
)
SELECT load_date, row_count, baseline,
       (row_count - baseline) / NULLIF(sd, 0) AS z_score
FROM scored
WHERE ABS((row_count - baseline) / NULLIF(sd, 0)) > 3;

A z-score is sensitive to outliers. Median and median absolute deviation are more robust, which is an easy point to raise given your degree.

Deleting data from immutable storage

This is a classic design question: how do you honor an erasure request in a lake built on immutable files?

  1. Keep a mapping that shows which tables hold each person's data.

  2. Delete with DELETE or MERGE on a table format.

  3. Rewrite the affected files, since a delete alone may leave the old data in earlier snapshots.

  4. Expire the old snapshots and remove the orphan files.

  5. Handle bronze too. Crypto-shredding helps here: encrypt per subject and destroy the key.

  6. Remember backups, Kafka topics, and downstream copies.

  7. Log evidence of completion without retaining the data itself.

Performance triage

Pipelines for retrieval and LLM applications

A RAG index is a derived dataset. Treat it with the same discipline as any other table.

  1. Ingest documents and record the source, version, and permissions.

  2. Parse PDFs, HTML, and other formats. This is usually the hardest step.

  3. Clean by removing boilerplate and detecting personal data.

  4. Chunk the content, keeping metadata and links back to the source.

  5. Embed with a named, versioned model.

  6. Index in a vector store, together with keyword search.

  7. Refresh incrementally using content hashes, and remove deleted documents.

  8. Evaluate retrieval against a labeled test set.

import hashlib

def chunk_id(doc_id: str, position: int, text: str, embed_model: str) -> str:
    # Stable IDs make upserts idempotent and show which chunks changed.
    key = f'{doc_id}|{position}|{embed_model}|{text}'
    return hashlib.sha256(key.encode()).hexdigest()

Key points that are easy to miss:

  • Changing the embedding model usually means re-embedding everything, so plan for it and store the version.

  • Access control must follow documents into the index, or the search will leak restricted content.

  • A deleted source document must also be removed from the index.

  • Compare costs for embedding, storage, and queries.

For agent access, combine a governed semantic layer, least-privilege roles, query cost limits, audit logs, and defenses against prompt injection in retrieved data. Your prompt injection knowledge is directly relevant.

Using AI in your own work

AI tools write SQL quickly, and they also make confident grain and join mistakes. Keep these habits:

  • Run a grain test and a row-count check on any AI-written query.

  • Ask for tests along with the code.

  • Never paste sensitive or employer data into an unapproved tool.

  • Learn the fundamentals by hand first. Interviews often ban assistants, and you must be able to spot errors.

Data system design interviews test whether you can turn a vague need into a pipeline that stays correct under failure, and whether you can justify each trade-off. A clear process matters more than naming the newest tools.

Use this as your default sketch, then remove anything the requirements do not justify. Many companies never need the low-latency path.

Five practice designs

1. Clickstream analytics

For 500 million events a day with dashboards under 15 minutes old. Collect events through an API into Kafka, using a schema registry. Land raw data in bronze through a sink, process it with Spark or Flink into sessionized silver tables, and serve gold aggregates to BI. Deep dives: bot filtering, late mobile events, sessionization across day boundaries, and compaction.

2. Change data capture to a lakehouse

For replicating a busy operational SQL Server into Iceberg or Delta tables. Use log-based CDC through Debezium and Kafka, apply changes in order with MERGE, and retain raw change logs in bronze. Deep dives: the initial snapshot, ordering by log sequence number, deletes, schema changes, and merge-on-read compaction.

3. Real-time fraud features

This fits your background well. For scoring transactions in under 100 ms using features such as count of transactions in the past 10 minutes. Flink computes windowed features from Kafka, pushes them to an online store such as Redis, and writes the same features to the lakehouse for training. Deep dives: consistency between online and offline features, state recovery, and fallback behavior when features are stale.

4. Company-wide metrics platform

For consistent revenue and active-user figures across teams. Use conformed dimensions, a semantic layer, dbt tests, and certified gold tables with owners. Deep dives: metric versioning, restating history, and handling a changed definition.

5. Multi-tenant data platform

For 50 teams sharing infrastructure. Provide templates, a governed catalog, per-team quotas, cost reports, and self-service access. Deep dives: noisy neighbors, permissions, and how a team deploys without tickets.

A model answer: "How do you make a pipeline idempotent?"

Idempotent means a rerun gives the same result as a single run. First, I parametrize each run by its logical date rather than the current time. Then I choose a write strategy that fits the data: partition overwrite for a daily fact table, or a merge on a stable key for a mutable entity. I also dedupe the input, because sources can send duplicates. I'd prove it with a test that runs the load twice and compares the output. On one past incident, a replay mechanism recovered messages, so the receiving side also had to tolerate seeing them twice.

Check the final sentence against what truly happened before using it. Notice the shape of the answer: define it, give the mechanism, give the trade-offs, prove it, and add experience.
